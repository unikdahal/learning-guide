A 64-bit integer column spends 64 bits on every value, but very few columns need them. Quantities fit in 7
bits, a status code in 2, and a column of timestamps, each a 41-bit number, changes by a few hundred
milliseconds from one row to the next. **Lightweight encodings** exploit that structure with simple
arithmetic: no dictionaries of byte sequences, no entropy coding, just a few operations per value. They are
cheap enough to decode at memory speed, which is why every columnar file format is built on them, and why
they sit underneath the general-purpose compression of the [next article but one](../general-purpose-compression/).

## The question

What are the basic lightweight encodings, which kinds of data does each suit, and how do they combine?

## Four ideas

- **Bit-packing** stores every value in the number of bits the largest one needs, back to back across word
  boundaries. Values 1 to 100 need 7 bits each, so 64 of them fit in 56 bytes instead of 512.
- **Frame of reference** (FOR) subtracts a reference value, usually the minimum, and bit-packs the
  differences. Only the spread of the values matters, not their size: prices between 10,000 and 10,500 need
  9 bits, where plain bit-packing would need 14.
- **Delta encoding** stores the first value and then the difference from each value to the previous one.
  Sorted or slowly changing data turns into small numbers, which are then bit-packed.
- **Run-length encoding** (RLE) stores each run of equal values once, with its length.

## Measured: five columns, five encodings

The lab encodes five columns of 10 million `Int64` values each. The implementations are written plainly in
[`encodings.rs`](https://github.com/unikdahal/learning-guide/blob/main/lab/crates/m03-representation/src/encodings.rs),
each a few dozen lines; "FOR/1024" applies frame of reference separately to each block of 1,024 values,
with its own minimum and width, and the delta encoding packs its differences the same way.

```text title="cargo run --release -p m03-representation --example encodings"
bits per value (10000000 values each; plain Int64 is 64)

column                         bitpack       FOR   FOR/1024     delta       RLE
event time, sorted ms            41.00     33.00      19.15     10.07     95.90
quantity, 1 to 100                7.00      7.00       7.07      8.07     95.04
price in cents, 10000-10500      14.00      9.00       9.07     10.07     95.81
status, runs of ~1000             2.00      2.00       0.92      1.01      0.07
hash, random 64-bit                n/a     64.00      64.07     64.07     96.00
```

Reading down the columns:

- **Timestamps** need 41 bits each because they are large. Subtracting the column's minimum saves only 8
  bits, because over 10 million rows they span about 58 days. Per-block minimums do better, 19 bits, because
  each block of 1,024 rows spans only minutes. Delta encoding stores the gaps between orders, under a second,
  in about 10 bits: 6.4 times smaller than plain.
- **Quantities** are already small; bit-packing gets them to 7 bits and nothing improves on it. Delta is
  worse, because the difference between two random quantities ranges from −99 to 99 and needs 8 bits.
- **Prices** show what frame of reference is for: 501 possible values starting at 10,000, so 9 bits instead
  of 14.
- **Status codes** in long runs are what RLE is for: 0.07 bits per value, 7,308 runs for 10 million rows.
  Everywhere else RLE is a disaster, 95 bits per value, because each run costs 96 bits and runs are length 1.
- **Random hashes** can't be encoded at all. Every scheme stays at 64 bits or adds a little overhead.

<Aside type="note" title="Outliers and patching">
One value far from the rest, a single 40-bit number among 7-bit ones, forces bit-packing and frame of
reference to use 40 bits for the whole block. Block-wise encoding limits the damage to one block. Patched
schemes go further: PFOR, from Marcin Zukowski and colleagues in 2006, packs most values narrowly and stores
the few exceptions separately, to be patched in after unpacking.
</Aside>

## Measured: decoding

Decoding has to be fast, or the encoding just trades disk space for CPU time:

```text title="cargo run --release -p m03-representation --example encodings"
plain copy                                 14.49 ms  (memcpy of plain Int64, for scale)
FOR/1024, quantity (7 bits)                23.39 ms   2.34 ns/value    3.4 GB/s of Int64 out
FOR/1024, price (9 bits)                   16.15 ms   1.61 ns/value    5.0 GB/s of Int64 out
delta, event time (10 bits)                32.84 ms   3.28 ns/value    2.4 GB/s of Int64 out
RLE, status                                13.24 ms   1.32 ns/value    6.0 GB/s of Int64 out
```

These are the lab's plain scalar decoders, one value per loop iteration, and they are slower than copying
plain data that is already in memory. That isn't the comparison that matters, though: the encoded data is 7
to 9 times smaller, so when it comes from disk, the network or even DRAM, much less has to arrive. And
production decoders are much faster than these. Daniel Lemire and Leonid Boytsov's 2015 paper is titled
"Decoding billions of integers per second through vectorization", and the FastLanes layout from Azim Afroozeh
and Peter Boncz (VLDB 2023) arranges bit-packed values so that SIMD registers unpack many at once. The delta
decoder is the slowest here because each value depends on the previous one, the
[dependency chain](../../hardware/instruction-level-parallelism/) problem; fast implementations compute
prefix sums in SIMD registers or interleave several independent chains.

Some operations don't need to decode at all. The sum of the run-length encoded status column, computed per
run:

```text title="cargo run --release -p m03-representation --example encodings"
status: plain sum 11.35 ms, sum over 7308 runs 0.0046 ms
```

## Combining encodings

Lightweight encodings stack, and real formats are mostly combinations:

- **Delta, then frame of reference, then bit-packing**: the lab's delta encoding, and the shape of Parquet's
  `DELTA_BINARY_PACKED`. Its blocks are a multiple of 128 values; each block stores its minimum delta, then
  miniblocks whose sizes are multiples of 32 values, each bit-packed with its own width.
- **Dictionary, then RLE and bit-packing**: Parquet's default for most columns. Values become dictionary
  codes ([dictionary encoding in storage](../dictionary-encoding-in-storage/)), and the codes are stored with
  a hybrid that switches between runs, for repeated codes, and bit-packed groups of 8, for varying ones.
  Parquet uses the same hybrid for the repetition and definition levels of nested data.
- **Lightweight, then general-purpose**: a page of encoded values can still be compressed with LZ4 or Zstd,
  which find patterns these schemes don't.

Floating-point numbers need their own tricks, because their bit patterns don't form small differences.
Parquet's `BYTE_STREAM_SPLIT` reorders the bytes of each value so a general compressor sees similar bytes
together, and newer schemes such as ALP (Afroozeh, Kuffó and Boncz, SIGMOD 2024) turn decimal-like doubles
back into integers that encode well.

## Costs and trade-offs

**Each scheme bets on one structure.** Small values, a narrow range, smooth changes or long runs. Choosing
the wrong one costs space; writers often try several per page and keep the smallest.

**Order matters.** Sorting a column, or a table by that column, creates runs and small deltas. The same data
in random order may not encode at all.

**Random access gets harder.** Finding value i in a bit-packed block is arithmetic; in delta or RLE data it
means decoding from the start of the block or searching run boundaries. Formats keep blocks small for that
reason.

## Check yourself

<details>
<summary>A column holds values from 1,000,000 to 1,000,300. How many bits per value with bit-packing, and with frame of reference?</summary>

Bit-packing needs the width of the largest value, about 1,000,300, which is 20 bits. Frame of reference
subtracts 1,000,000 and packs 0 to 300 in 9 bits.
</details>

<details>
<summary>Why did delta encoding make the quantity column larger than frame of reference did?</summary>

Quantities are random from 1 to 100, so the difference between neighbours ranges from −99 to 99: a spread of
199, needing 8 bits, against 7 bits for the values themselves.
</details>

<details>
<summary>Why is a delta decoder harder to speed up than a frame-of-reference decoder?</summary>

Each decoded value is the previous one plus a difference, a chain of dependent additions. Frame of reference
adds the same constant to every value independently, so many values can be processed at once.
</details>
