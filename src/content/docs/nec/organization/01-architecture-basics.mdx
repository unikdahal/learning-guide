## 1. Architecture vs organisation

- **Computer architecture** = the attributes **visible to the programmer** that affect how a program runs: the instruction set, data types and sizes, addressing modes, number of registers, I/O mechanisms. *Does this machine have a multiply instruction?* is an architecture question.
- **Computer organisation** = **how** those attributes are implemented, invisible to the programmer: control signals, the interface between units, memory technology, whether multiply is done by a hardware multiplier or by repeated addition.

The classic example: every x86 chip from the 8086 onwards shares an architecture (old programs still run), but their organisations differ enormously (pipelines, caches, out-of-order execution). Same contract, different implementation — like an interface and its implementations.

## 2. The stored-program idea: von Neumann and Harvard

<Figure caption="von Neumann (one memory, one bus for both instructions and data) vs Harvard (separate memories and paths).">
  <DigitalDiagram name="vn-harvard" label="Left: von Neumann — a CPU connected by one shared bus to a single memory holding both instructions and data. Right: Harvard — a CPU with two separate paths, one to an instruction memory and one to a data memory." />
</Figure>

**von Neumann architecture** (stored-program concept, 1945):
- Program and data live in the **same memory**, reached over the **same bus**.
- Instructions run **sequentially** from the program counter.
- Five parts: input, output, memory, ALU, control unit (CPU = ALU + CU + registers).
- Weakness: the **von Neumann bottleneck** — instruction fetch and data access queue for one bus, so the CPU waits on memory.

**Harvard architecture:**
- **Separate** instruction and data memories with separate buses, so an instruction fetch and a data access can happen in the **same cycle**.
- Used in DSPs and microcontrollers (8051, AVR, PIC).
- **Modified Harvard** — what your laptop actually is: one main memory (von Neumann for the programmer) but **split L1 instruction and data caches** inside the CPU.

## 3. The CPU and its registers

- **ALU** — arithmetic and logic operations; sets the status flags.
- **Control unit** — decodes instructions and issues the control signals that sequence everything (lesson 3).
- **Registers:**

| Register | Holds |
| --- | --- |
| **PC** (program counter) | address of the next instruction |
| **IR** (instruction register) | the instruction being executed |
| **MAR** (memory address register) | the address sent to memory |
| **MBR / MDR** (memory buffer/data register) | the word read from or written to memory |
| **AC** (accumulator), general registers | operands and results |
| **PSW / flags** | status bits (zero, carry, sign, overflow) and interrupt enable |
| **SP** | top of the stack |

## 4. Bus structures

A **bus** is a shared group of wires. The **system bus** has:
- **Address bus** — one-way; width sets the addressable memory (16 lines → 64 K, 32 lines → 4 G).
- **Data bus** — two-way; width sets how many bits move per transfer (the "word size" of the bus).
- **Control bus** — read, write, clock, interrupt request/acknowledge, bus request/grant.

Bus organisations: **single bus** (cheap, one transfer at a time), **multiple buses / hierarchical** (a fast processor–memory bus plus slower expansion buses joined by bridges — every PC). **Synchronous** buses use a clock; **asynchronous** buses use handshaking (request/acknowledge).

**Bandwidth** = data width × transfer rate. A 64-bit bus at 100 MHz moving one word per cycle → 8 bytes × 100 M = **800 MB/s**.

## 5. Register transfer notation (RTL)

Exam answers describe micro-operations in RTL:
- `R2 ← R1` — copy R1 into R2.
- `P: R2 ← R1` — only when control condition P = 1.
- `AC ← AC + DR`, `M[AR] ← DR` (write memory at the address in AR), `DR ← M[AR]` (read).
- Micro-operations separated by commas happen in the **same** clock.

## 6. The instruction cycle

Each instruction passes through these phases, driven by timing signals T0, T1, T2 …:

| Phase | Register transfers (Mano's basic computer) |
| --- | --- |
| **Fetch** | T0: `AR ← PC` · T1: `IR ← M[AR], PC ← PC + 1` |
| **Decode** | T2: decode opcode `IR(12–14)`, `AR ← IR(0–11)`, `I ← IR(15)` |
| **Indirect** (if I = 1) | T3: `AR ← M[AR]` — fetch the operand's real address |
| **Execute** | e.g. ADD: `DR ← M[AR]` then `AC ← AC + DR` |
| **Interrupt** (if enabled and pending) | save PC: `M[0] ← PC`, `PC ← 1`, `IEN ← 0` |

Then back to fetch. The **instruction cycle** is the whole loop; the **fetch cycle** and **execute cycle** are its two main parts (some books add indirect and interrupt cycles). Each phase takes one or more **machine cycles**, and each machine cycle takes several **clock cycles (T-states)** — exactly as you saw for the [8085](/learning-guide/nec/digital/11-8085/).

**Performance equation:** CPU time = instruction count × CPI × clock period. A faster clock, fewer instructions (CISC) or fewer cycles per instruction (RISC, pipelining) each help — but usually trade against the others.
