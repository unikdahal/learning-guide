## 1. Operator overloading

**Operator overloading** gives an existing operator a user-defined meaning for class types (`c1 + c2` for complex numbers) — compile-time polymorphism. Syntax: `ReturnType operator symbol (parameters)`.

```cpp
class Complex {
    double re, im;
public:
    Complex(double r = 0, double i = 0) : re(r), im(i) {}
    Complex operator+(const Complex& o) const { return Complex(re + o.re, im + o.im); }  // binary, member
    Complex& operator++()    { ++re; return *this; }                                     // prefix ++c
    Complex  operator++(int) { Complex t = *this; ++re; return t; }                      // postfix c++ (dummy int)
    friend ostream& operator<<(ostream& os, const Complex& c) { return os << c.re << "+" << c.im << "i"; }
};

Complex x(1, 2), y(3, 4);
cout << x + y;      // 4+6i
cout << x++;        // 1+2i  (returns the old value; x is now 2+2i)
cout << ++x;        // 3+2i
```

Rules:
- A **member** binary operator takes **one** argument (the left operand is `*this`); a **friend** binary operator takes **two**. Member unary: none; friend unary: one.
- Operators that **can't be overloaded:** `::` (scope), `.` (member access), `.*`, `?:` (ternary), `sizeof`, `typeid`.
- `=`, `()`, `[]`, `->` must be **members**. `<<` and `>>` for streams must be **non-members** (usually friends), since the left operand is a stream.
- You can't create new operators or change precedence, associativity or arity.

## 2. Data conversion

| Conversion | How |
| --- | --- |
| basic → class | a **constructor** taking the basic type: `Meter(double v)` lets `Meter m = 5.5;` |
| class → basic | a **conversion operator**: `operator double() const { return m; }` lets `double d = m;` (prints 5.5) |
| class → class | a constructor in the destination class taking the source, **or** a conversion operator in the source class |

Mark single-argument constructors `explicit` to prevent unwanted implicit conversions.

## 3. Inheritance

A **derived** class acquires the members of a **base** class ("is-a"): reuse and extension.

**Types:** **single** (A → B), **multiple** (A, B → C), **multilevel** (A → B → C), **hierarchical** (A → B, A → C), **hybrid** (a combination), **multipath** (D inherits from B and C, which both inherit from A — the **diamond**).

**Visibility modes** — how base members appear in the derived class:

| Base member | public inheritance | protected inheritance | private inheritance |
| --- | --- | --- | --- |
| public | public | protected | private |
| protected | protected | protected | private |
| private | **not accessible** | not accessible | not accessible |

Private base members are always inherited but **never directly accessible** in the derived class.

### Constructor and destructor order

**Constructors run base → derived; destructors run derived → base.** In multiple inheritance, bases construct in the order they're **listed in the class declaration**.

```cpp
struct Base    { Base()    { cout << "Base() "; }    virtual ~Base()    { cout << "~Base() "; } };
struct Derived : Base { Derived() { cout << "Derived() "; } ~Derived() { cout << "~Derived() "; } };
Base* p = new Derived();   // Base() Derived()
delete p;                  // ~Derived() ~Base()   (because ~Base is virtual)
```

Arguments reach a base constructor through the derived constructor's initialiser list: `Derived(int x) : Base(x) {}`.

### Multipath (diamond) inheritance and virtual base classes

```cpp
struct A  { A()  { cout << "A "; } };
struct B2 : A { B2() { cout << "B2 "; } };
struct C2 : A { C2() { cout << "C2 "; } };
struct D2 : B2, C2 { D2() { cout << "D2 "; } };     // A B2 A C2 D2  — two copies of A!

struct B : virtual A { B() { cout << "B "; } };
struct C : virtual A { C() { cout << "C "; } };
struct D : B, C { D() { cout << "D "; } };          // A B C D       — one shared A
```

Without `virtual`, D2 contains **two A sub-objects** — wasted space and **ambiguity** (`d2.member_of_A` won't compile). Declaring A as a **virtual base class** makes B and C share one A; the most-derived class constructs it first.

### Composition ("has-a") vs inheritance ("is-a")

**Composition** builds a class from **member objects** of other classes — a Car *has an* Engine. The parts are constructed **before** the whole's constructor body and destroyed **after** its destructor:

```cpp
class Engine { public: Engine() { cout << "Engine() "; } ~Engine() { cout << "~Engine() "; } void start() { cout << "vroom "; } };
class Car {
    Engine engine;                     // composition: lives and dies with the Car
    std::string model;
public:
    Car(std::string m) : model(m) { cout << "Car() "; }
    ~Car() { cout << "~Car() "; }
    void drive() { engine.start(); }   // delegation
};
{ Car c("Swift"); c.drive(); }          // Engine() Car() vroom ~Car() ~Engine()
```

| Inheritance | Composition |
| --- | --- |
| "is-a" (Circle is a Shape) | "has-a" (Car has an Engine) |
| reuse by extending the base's interface | reuse by delegating to a member |
| fixed at compile time; tight coupling to the base | parts can be swapped (e.g. via pointers/interfaces); looser coupling |
| supports polymorphic substitution | no substitution by itself |

Guideline: **"favour composition over inheritance"** unless there's a genuine is-a relationship. **Aggregation** is the weaker form — the part can exist independently (a Department *has* Professors held by pointer/reference; deleting the department doesn't delete them). In UML: composition = filled diamond ◆, aggregation = hollow diamond ◇.

## 4. Polymorphism: virtual functions and dynamic binding

**Polymorphism** = "many forms": **compile-time** (function and operator overloading, templates) vs **run-time** (virtual functions).

```cpp
struct Base    { void show() { cout << "Base::show "; }    virtual void vshow() { cout << "Base::vshow "; } };
struct Derived : Base { void show() { cout << "Derived::show "; } void vshow() override { cout << "Derived::vshow "; } };

Base* p = new Derived();
p->show();    // Base::show     — non-virtual: chosen by the POINTER type at compile time (static binding)
p->vshow();   // Derived::vshow — virtual: chosen by the OBJECT type at run time (dynamic binding)
```

- Declare with **`virtual`** in the base; a derived function with the same signature **overrides** it (`override` asks the compiler to check). Calls through a **base pointer or reference** dispatch on the actual object.
- Implemented with a **vtable** (per class, table of function addresses) and a **vptr** in each object — so a class with virtual functions grows by a pointer (`sizeof(Base)` = 8 here: just the vptr).
- **Overriding vs overloading:**

| Overloading | Overriding |
| --- | --- |
| same name, **different parameters** | same name **and signature** in a derived class |
| same scope (or class) | base and derived classes |
| resolved at **compile time** | resolved at **run time** (if virtual) |
| return type may differ | return type same (or covariant) |

- **Effect of overriding:** the derived class's version replaces the base version for objects of the derived class — through a base pointer only if the function is virtual.
- **Pure virtual function:** `virtual double area() = 0;` — no body required. A class with at least one is an **abstract class**: it **can't be instantiated**, only used as a base (an interface). Derived classes must override every pure virtual function to become concrete.
- **Virtual destructor:** if you `delete` a derived object through a base pointer, the base destructor **must be virtual** — otherwise only `~Base()` runs (undefined behaviour, leaks).
- Constructors **can't** be virtual.
