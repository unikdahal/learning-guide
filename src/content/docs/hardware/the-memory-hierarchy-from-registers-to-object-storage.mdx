Module 01 treated data as if every value were equally close at hand. In a real machine, where a value lives
decides how long it takes to reach, and the range is absurd: the same 64 bytes can arrive in two nanoseconds
or in a tenth of a second, a factor of fifty million. A query engine that touches its data in the wrong order
or from the wrong place wastes most of its time waiting.

This module is about the machine, and this first article draws the map. Instead of quoting a table of numbers
from a slide, it measures this guide's own lab machine, level by level, and shows where the measurements are
clean and where they are puzzling.

## The question

How long does it take to reach data at each level of the machine, how much can each level deliver per second,
and why are there levels at all?

## Why a hierarchy exists

Fast memory is small and expensive; big memory is slow. A register holds a few bytes and can be read every
cycle; DRAM holds gigabytes and takes about a hundred nanoseconds to answer. No technology is both, so
machines stack several: a few small, fast caches near each core, a larger shared cache, main memory, then
storage and the network. Each level keeps copies of the data the level above it recently needed, betting that
it will be needed again soon (**temporal locality**) or that its neighbours will be (**spatial locality**).
When the bet pays, the data comes from the fast level; when it doesn't, from the next one down.

## Measuring latency: a pointer chase

To measure how long one access takes, the access must not overlap with others. Modern CPUs run many loads at
once, so a loop that reads an array would measure bandwidth, not latency. The standard trick is a **pointer
chase**: an array of nodes, each holding the index of the next node to visit, linked into one random cycle.

```rust
// lab/crates/m02-hardware/src/lib.rs
pub fn chase(nodes: &[Node], steps: usize) -> usize {
    let mut i = 0;
    for _ in 0..steps {
        i = nodes[i].next; // the next address depends on this load's value
    }
    i
}
```

Each load needs the previous load's value to know where to go, so the CPU can't start the next one early. The
cycle is random, so no prefetcher can guess the next address. Each node fills a whole 64-byte cache line, so
every step touches a new line. The time per step is then the latency of one memory access, for a working set
of a given size. The lab varies that size from 4 KiB to 1 GiB, and repeats each point at least three times
(seven for the smaller sizes), reporting the median.

## What the lab machine reports

The lab runs on a 2-core cloud VM with an Intel Xeon (family 6, model 207, under KVM). The kernel describes
its caches like this:

```text title="/sys/devices/system/cpu/cpu0/cache"
L1 data          48 KiB   64-byte lines   12-way
L1 instruction   32 KiB   64-byte lines    8-way
L2 unified        2 MiB   64-byte lines   16-way
L3 unified      260 MiB   64-byte lines   20-way
```

And here is the chase:

```text title="cargo run --release -p m02-hardware --example latency (trimmed)"
working set   ns / load
      4 KiB        2.09
     16 KiB        1.96
     32 KiB        2.07
     64 KiB        5.46
    256 KiB        5.99
      1 MiB        6.90
      2 MiB       24.74
      4 MiB       36.32
      8 MiB       37.18
     16 MiB      127.95
     64 MiB      135.86
    256 MiB      152.55
      1 GiB      174.51
```

The steps are clear. Up to 32 KiB, the working set fits in the 48 KiB L1, and a load takes about 2 ns. From 64
KiB to 1 MiB it fits in the 2 MiB L2: about 6 ns. Then a third level at about 37 ns, then main memory at 128 ns
and rising.

## Two surprises, and what they teach

**The third level is small.** The kernel reports a 260 MiB L3, but latency leaves the 37 ns level somewhere
between 8 and 16 MiB. The measurement can't say why, and it is worth being exact about what is fact and what
is guess. Fact: the chase shows a step at 8–16 MiB and the hardware description says 260 MiB. Hypotheses: a VM
sees the host's full cache description but shares the cache with other tenants; on large Intel server chips
the L3 is split into slices spread over a mesh, so latency depends on which slice holds a line; and the
bandwidth test below finds a different boundary. Without hardware performance counters, which this VM doesn't
expose, the lab can't tell these apart. The lesson is general: measure your machine; don't infer from the
spec sheet.

**Main memory gets slower as it gets bigger.** From 16 MiB to 1 GiB, latency climbs from 128 to 175 ns. Part of
that isn't memory at all, but **address translation**. Programs use virtual addresses, and each access needs
the physical address, cached in a small table called the TLB. With ordinary 4 KiB pages, a large random working
set misses the TLB constantly, and each miss costs a walk through page tables. The lab repeats the chase on 2
MiB huge pages, where each TLB entry covers 512 times as much memory:

```text title="cargo run --release -p m02-hardware --example tlb (trimmed)"
working set   4 KiB pages   2 MiB pages     huge-backed
      2 MiB       26.2 ns       11.8 ns            100%
      8 MiB       37.7 ns       33.4 ns            100%
     16 MiB      126.7 ns      121.7 ns            100%
    256 MiB      153.2 ns      126.2 ns            100%
      1 GiB      178.9 ns      131.0 ns            100%
```

With huge pages, main memory sits flat at 121 to 131 ns, and the 2 MiB working set drops from 26 to 12 ns. The
step at 16 MiB stays, so it is a real cache boundary, not a translation effect. But up to 48 ns per access at 1
GiB was address translation. [TLBs, pages and huge pages](../tlbs-pages-and-huge-pages/) covers this properly.

## Bandwidth: a different question

Latency asks how long one access takes. **Bandwidth** asks how many bytes per second a level can deliver when
the program asks for many at once, in order. The lab sums a buffer of each size, on one thread:

```text title="cargo run --release -p m02-hardware --example latency (trimmed)"
working set      GB / s
     32 KiB        63.8
    256 KiB        55.3
      1 MiB        54.3
      4 MiB        28.0
     32 MiB        28.4
     64 MiB        26.8
    128 MiB         9.7
      1 GiB         9.2
```

Three plateaus: about 55 to 64 GB/s from L1 and L2, 28 GB/s from the next level, and 9 GB/s from memory. This
level stays fast up to 64 MiB, while the chase fell to memory speed at 16 MiB, which is the disagreement
mentioned above. Sequential access hides latency in ways a chase can't, with hardware prefetchers fetching
ahead and many requests in flight at once, so the two tests don't measure the same thing.

Compare the two numbers for main memory. A chase brings in one 64-byte line every 128 ns: 0.5 GB/s. A
sequential scan brings in 9 GB/s, eighteen times as much, from the same memory. The difference is entirely in
the access pattern: in order, the hardware can see what's coming and overlap the waits. Much of query engine
design, from columnar formats to vectorized execution, is about making accesses look like the second pattern.

## Below main memory

The lab measures two more rungs, reading a 1 GiB file:

```text title="cargo run --release -p m02-hardware --example storage"
disk, O_DIRECT (no page cache)     median      40.8 µs   p99      95.1 µs   (2000 reads)
page cache (file data in RAM)      median       0.8 µs   p99       1.2 µs   (20000 reads)

read 1 GiB in 0.48 s: 2239 MB/s
```

A random 4 KiB read from this VM's virtual disk takes about 41 µs, three hundred times main memory's latency.
With `O_DIRECT`, the read skips the operating system's page cache; without it, a block already cached in RAM
comes back in 0.8 µs, which is mostly the cost of the system call and the copy, not of memory. Sequential reads
in 1 MiB pieces reach 2.2 GB/s. A cloud VM's disk is usually network-attached, so these numbers describe this
machine, not SSDs in general; [Disks and SSDs](../disks-and-ssds/) goes further.

The bottom rung is object storage, which the lab can't reach. Amazon's S3 documentation says latency-sensitive
applications "can achieve consistent small object latencies (and first-byte-out latencies for larger objects)
of roughly 100–200 milliseconds", and that throughput comes from parallelism: "at least 3,500
PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix", with single
instances reaching "up to 100 Gb/s". A request costs a hundred milliseconds whether it fetches a kilobyte or
megabytes, so engines reading from object storage make requests large and issue many at once.

<Aside type="note" title="Orders of magnitude worth memorizing">
From this machine: about 2 ns for L1, 6 ns for L2, 40 ns for the next level, 130 ns for main memory, a
microsecond for a cached file read, tens of microseconds for a disk read, and, from AWS, a hundred milliseconds
or more for an object storage request. Your machine will differ in the details; the ratios are what to carry
around.
</Aside>

## What this means for query engines

Every later module leans on this map.

- **Scans** are bandwidth-bound: a columnar format reads only the needed columns, so fewer bytes cross the
  slowest boundary ([Module 03](../../data-representation/)).
- **Hash tables** are latency-bound: each probe is a random access, so a table that fits in cache is several
  times faster per probe than one that doesn't, which motivates partitioned joins
  ([Module 08](../../joins/)).
- **Compression** trades CPU time for fewer bytes moved, worth it whenever bandwidth, not computation, is the
  limit.
- **Remote storage** is latency-bound per request and bandwidth-rich in aggregate, which shapes how lakehouse
  engines plan their reads ([Module 07](../../scans-and-pruning/)).

## Costs and trade-offs

**Locality is the cheapest optimization.** Touching data in order and keeping working sets small speeds up
every level at once, and costs nothing in hardware.

**Averages hide the shape.** A single "memory latency" number misses the steps, the translation overhead and the
difference between random and sequential access. Measure the pattern your code actually has.

**Clouds add a layer of uncertainty.** A VM may see hardware descriptions that don't match its share of the
hardware, and noisy neighbours change results from run to run. Repeat, report medians and noise, and say what
machine produced the numbers.

## Check yourself

<details>
<summary>Why does the pointer chase link its nodes in a random cycle, rather than in order?</summary>

In order, the hardware prefetcher would recognize the pattern and fetch lines before they are needed, and the
test would measure something much faster than real latency. A random cycle gives the prefetcher nothing to
predict.
</details>

<details>
<summary>Main memory delivered one line every 128 ns to the chase, but 9 GB/s to a sequential scan. Explain the difference.</summary>

The chase has one access in flight at a time, because each address depends on the previous load. The scan's
addresses are known in advance, so the CPU and its prefetchers keep many requests in flight and overlap their
latencies.
</details>

<details>
<summary>Huge pages lowered latency at 1 GiB from 179 to 131 ns but left the step at 16 MiB in place. What does each observation tell you?</summary>

The drop at 1 GiB is time that was spent on address translation: TLB misses and page walks, which huge pages
reduce. The step at 16 MiB survives huge pages, so it isn't a translation effect but a real boundary between a
cache level and main memory.
</details>

<details>
<summary>An engine reads a table stored as 10,000 objects of 1 MiB each in object storage, one request at a time. Roughly how long does it spend waiting, and what would you change?</summary>

At about 100 ms per request, 10,000 sequential requests wait about 1,000 seconds. Issue many requests in
parallel, and prefer fewer, larger objects or byte ranges, so latency overlaps and bandwidth becomes the limit.
</details>
